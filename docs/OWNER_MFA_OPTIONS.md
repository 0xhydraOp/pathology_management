Google account 2FA strengthens the account, but is not automatically proof in an Access token. Google's current [OIDC guide](https://developers.google.com/identity/openid-connect/openid-connect) describes optional `amr`; the [Security Bundle](https://developers.google.com/identity/siwg/security-bundle), listed under Early Access, requires a published/verified OAuth app, enabled advanced settings and the authentication request claim. Evidence can still be absent. Its older [reference claim list](https://developers.google.com/identity/openid-connect/reference) does not list `amr`; do not treat either a basic Google login or a claim-forwarding setting as a guarantee of receipt. Native Access Google integration's documented configuration does not establish that the necessary Google request is sent. No Google Security Bundle dependency is recommended for the first rollout.

Cloudflare documents [independent MFA](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/independent-mfa/) with WebAuthn keys/platform authenticators and [per-app enforcement](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/mfa-requirements/). These describe an enforced challenge, not a guaranteed signed independent-MFA field that our current verifier can consume. The public session API schemas inspected also do not specify an MFA completion field; this is a documentation gap, not proof that an actual token never contains evidence. Access currently returns not-enabled, so there is no real account token to certify under this read-only task.

## Application WebAuthn alternative — design proposal, not implemented

Retain Google Access identity, issuer/audience/signature/time checks, exact owner email/subject and host protection. Add a distinct approved MFA contract whose second proof is server-verified WebAuthn; the Google JWT alone permits only a metadata-free authentication shell/challenge. Every customer/licence/device/audit read and mutation, and every legacy CLI API, requires completed step-up. Disable unsupported CLI writes until it can supply the same short-lived proof; the existing admin token must not become an exemption.

Use a maintained audited WebAuthn library, not custom CBOR/signature code; verify Workers compatibility, dependency advisories and Free CPU performance before selection. [SimpleWebAuthn verification API](https://simplewebauthn.dev/docs/packages/server) is a candidate. Our proposed requirements:

- Exact RP ID `admin.molladigital.com` and origin `https://admin.molladigital.com`, never parent-domain scope. Require user presence and user verification; reject cross-origin/iframe ceremonies. Bind each cryptographically random, five-minute, single-use challenge to owner subject, validated Access-session context and registration/authentication purpose.
- Store credential ID, public key, authenticator metadata and correctly handled counter/backup flags, never authenticator private keys. Do not assume every synced passkey has an increasing nonzero counter. Recommend an independently controlled device-bound/platform or hardware authenticator rather than a sole key synced through the identity-provider account.
- Atomically consume challenges, update credentials/counters, create sessions and audit successful changes. Replay, concurrent consumption, wrong origin/RP, missing UV, wrong owner, stale Access context and malformed payload must fail without partial state.
- Session: random opaque ID, hashed in D1, at most 15 minutes and no longer than Access expiry, bound to subject and the validated Access token/session. Cookie `__Host-patholy_owner_mfa`, Secure/HttpOnly/SameSite=Strict/Path=/, no Domain attribute. Existing same-origin CSRF remains; no cross-origin owner API access. Logout, recovery and authenticator replacement revoke relevant sessions.
- Apply edge per-IP limits plus durable per-owner D1 attempt controls to challenge/verify/enroll/recovery. Starting technical proposal: five failed verifications per 15 minutes with bounded cooldown, five-minute challenges and request-size bounds. No permanent attacker-triggered lockout; counters cannot be reset by switching IPs/restarting a Worker. Actual thresholds/load are to be tested, not commercial defaults.
- First registration requires the verified owner Google identity **and** a one-use out-of-band enrollment authorization provisioned through the owner's strongly authenticated Cloudflare management account/protected local tooling. Store only its hash; do not send it through chat/email or expose unrestricted first-user enrollment. Later authenticator changes require an existing verified factor.
- Enroll two authenticators. Offer high-entropy, one-use recovery codes stored only as hashes, with plaintext shown once to the owner and kept offline separately. Recovery requires verified Google identity plus the recovery proof, is rate-limited/audited and grants only a tightly scoped new-factor enrollment flow; normal licensing administration resumes after successful new WebAuthn verification. Rotate recovery material and revoke prior sessions. If every factor/code is lost, remain locked until an explicitly audited Cloudflare-management recovery procedure; no email-only reset or hidden account.

Application trade-off: provides our own cryptographic proof without undocumented Access MFA fields, but adds credential/challenge/session/recovery tables, browser compatibility testing, dependency updates, operator recovery procedures and ongoing security review. It must pass independent bypass/replay/concurrency/recovery review before production. It does not touch the clinical database, desktop credentials or offline licence grants.
