## Authenticated one-use bootstrap

Bootstrap authority is the authenticated Cloudflare deployment operator, not an anonymous visitor. Confirm control of the fixed owner mailbox out of band before handing off setup material. A configured email string alone is not verification.

1. Apply the reviewed owner-auth D1 migration through its migration journal. Configure the maintained provider SDK and secret installation after separate approval. Retain the disabled/readiness gate until provider flows are certified.
2. On a trusted workstation create an existing, non-synchronized private parent directory outside the repository. On Windows verify OS ACLs; mode bits alone are insufficient. Prepare a config file containing only `ownerOrigin`, `outputParent` and `ownerEmailControlVerified:true`. The origin must be `https://admin.molladigital.com`; never place passwords or API secrets in this file.
3. Run `node licensing-worker/scripts/owner-bootstrap.mjs config-file --prepare-only` to inspect preparation without any remote operation. It creates a new restricted child directory containing a SQL file with a SHA-256 digest and a protected `owner-setup.secret.json` link file. The raw 256-bit token appears only in the protected link file, never stdout or arguments. This link is **not registered** and must not be delivered.
4. Only after deployment approval, reviewed D1 binding and migration, run the same command with `--register-remote` to generate a new token and register it through locally installed Wrangler using authenticated D1 administration. It sends a digest-only SQL file with `--remote --file --yes --json`, not a token on the command line. The 15-minute interval begins at generation, not file delivery. Previous pending links are invalidated; active or provisioning identities reject registration atomically. [D1 execution](https://developers.cloudflare.com/d1/get-started/).
5. Read the newest link file privately and deliver it only through a protected owner-controlled channel. The setup URL uses `/owner/setup#token=...`; the page must remove the fragment from history and exchange it only in a same-origin HTTPS request body. Never paste the link into chat, logs, tickets or screenshots. The owner chooses the password on the setup page and completes TOTP enrollment/verification before administrative access.

The tool performs no provider account operation. Do not run remote registration in this preparation task. A prepare-only link cannot later be registered by changing its label; remote mode generates/registers fresh material. If remote execution has an uncertain outcome, do not deliver the link or repeatedly rerun registration. Inspect D1 privately through authenticated deployment administration. Failed/uncertain provider provisioning locks the bootstrap state; never automatically adopt an existing user, clear an active identity or issue a public reset.

## Sessions, password changes and recovery

Use host-only `__Host-` session cookies with Secure, HttpOnly, Path=/ and a supported SameSite policy; omit Domain entirely. No parent-domain cookie may expose owner sessions to the public site or future services. Reject stale/revoked receipts, other users, direct service JWTs and incomplete factors. Rate-limit password, second-factor, bootstrap and recovery endpoints; keep errors non-revealing and secrets out of audit metadata.

The cookie and local MFA receipt have a twelve-hour maximum, but the provider access token can expire earlier. Automatic refresh is intentionally absent: expiry requires password and TOTP again, and the UI reports the ended session. Verify actual provider expiry settings during live certification rather than promising a twelve-hour usable session. Password/MFA/bootstrap attempts are bounded by persistent per-route account/IP limits; a pending MFA ceremony allows five code attempts. Maintenance endpoints require private capabilities and strong factor proof; there is no public reset-to-admin flow.

Password changes require fresh password and second-factor reauthentication. Invalidate all owner-session receipts/epochs with the authenticated audit, including other browsers, and revoke provider sessions. Provider revocation failures must not leave an old local owner session authorized or be reported as complete remote cleanup. Logout invalidates the receipt and clears the cookie; new access requires both factors again.

There is no hidden recovery user, password, TOTP seed or universal override. Protect deployment/provider operator accounts with MFA. Mailbox possession alone must not replace an enrolled second factor. Preserve licence, customer and audit records; never reset the licensing database to recover the owner.

During initial enrollment, the owner should save the original authenticator setup material in a separately protected encrypted offline recovery vault and rehearse restoration with synthetic material first. Restoring the original factor to a replacement authenticator preserves its existing pin and still requires the password; it is not a reset or bypass account. Protect this backup separately from the password and deployment credentials. The application does not retain or reveal the seed after enrollment. If the primary authenticator and its protected copy are lost, use the controlled replacement process below only after live certification and with the verified independent recovery factor. If both factors and their copies are lost, keep access blocked; this process cannot establish ownership.

### Implemented operator recovery and reconciliation

Migration `0006_owner_lifecycle.sql` adds immutable provider-user/external-ID pins, durable operations, epoch-bound operator tickets and serialized provider maintenance. Existing identities, licences, customer/device records and audits remain in place. Apply it through the migration journal, not by repeatedly executing ALTER statements.

Setup must verify an **independent WorkOS standalone TOTP recovery authenticator** before owner-data access. Enrolling or replacing it requires fresh password and primary TOTP proof. Keep its different secret on an independent protected device/recovery medium. This does not assume two simultaneous AuthKit login factors are supported.

Lost-primary recovery requires the current password, the previously verified recovery factor, and a private fifteen-minute one-use operator ticket. The server checks the exact pinned user, challenge, factor, purpose and epoch. It revokes local receipts/provider sessions, keeps the owner locked, removes old user-associated factors, obtains a fresh documented MFA-enrollment token and verifies the new primary. A restricted recovery cookie never grants customer/licence access. Completion records an authenticated audit and requires fresh normal login.

Provisioning persists an operation UUID and unique WorkOS external ID **before** creation. Retries reconcile only that ID; once bound, the user ID cannot change. Private provisioning reconciliation may repair initial enrollment only while neither primary nor recovery factor has ever been verified. It cannot reset an established owner. Unknown writes, timeout/revocation failures and late replies retain fail-closed state; fresh authenticated maintenance can resume without email adoption. Provider calls have a bounded timeout and durable lease; local completion rechecks epoch/operation ownership.

The WorkOS dashboard's team-member reset is not this application-user ceremony. There is no public signup/reset-to-admin flow, email-only recovery, hidden user or universal seed. If the current password or both authenticators/recovery copies are lost, or an already pinned WorkOS user is deleted, these flows cannot silently create a replacement owner. Preserve the database and seek separately verified provider/operator recovery.

See [OWNER_RECOVERY_AND_RECONCILIATION.md](OWNER_RECOVERY_AND_RECONCILIATION.md) for exact tooling, contracts, failure cases and connection steps. [Provider evidence](WORKOS_PROVIDER_EVIDENCE.md) distinguishes documented APIs, synthetic tests and pending live checks. WorkOS and D1 do not form a distributed transaction; unknown remote effects can require reconciliation or cleanup. No atomic rollback across both services is claimed.
