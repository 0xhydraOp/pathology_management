# WorkOS provider evidence and recovery constraints

Verified against official sources on **9 October 2026**. Research only: no provider account, credential, factor, paid product or Cloudflare setting was changed.

| Contract | Evidence and implementation consequence |
| --- | --- |
| Password then TOTP | The [authentication reference](https://workos.com/docs/reference/authkit/authentication) documents a pending authentication token, a challenged factor and the MFA-TOTP grant. Require the actual completed transaction, exact pinned user and resulting session receipt; neither email nor a JWT alone grants owner access. |
| User-associated TOTP | The [AuthKit MFA reference](https://workos.com/docs/reference/authkit/mfa) documents enrolling a new TOTP factor and listing factors. It does **not explicitly guarantee multiple simultaneously enrolled TOTP factors or their limits**. Plural list responses do not certify a two-authenticator recovery design. Confirm provider behavior before enabling it live. |
| Independent recovery authenticator | The [standalone factor reference](https://workos.com/docs/reference/mfa/factor) documents `/auth/factors/enroll`, optional `user_id`, factor retrieval and irreversible deletion. A standalone TOTP factor without `user_id` can be independently pinned in the application's recovery state without assuming a second AuthKit login factor. This is an integration design inference, still requiring live certification. Store only its factor ID/verification metadata in D1, never the seed. |
| Proving recovery possession | The [challenge reference](https://workos.com/docs/reference/mfa/challenge) documents challenging a factor and `verifyChallenge` returning validity and challenge metadata. Require `valid === true`, the exact pinned factor/challenge, a short-lived single-use application ceremony and rate limits. Challenge verification by itself does not establish password verification or authorize owner operations. |
| Uncertain provisioning | [Metadata/external IDs](https://workos.com/docs/authkit/metadata) documents identifiers unique within an environment, at most 64 characters. The [user API](https://workos.com/docs/reference/authkit/user) supports create with `external_id` and exact external-ID lookup. Persist a random operation identifier before provider creation; reconcile only that identifier, fixed verified email and expected local operation state. Never adopt an account through email search. |
| Write retries | The [official Python SDK](https://github.com/workos/workos-python) states that API idempotency keys are currently honored only for creating audit-log events. Do not assume user/factor creation is idempotent because an SDK sends a key. Disable blind retries and use durable reconciliation/fail-closed states. |
| Password/session changes | The [user API](https://workos.com/docs/reference/authkit/user) permits password update on an exact user ID. The [session API](https://workos.com/docs/reference/authkit/session) supports listing and revoking sessions. Revoke all pages; invalidate local epochs/receipts before uncertain provider changes, then certify completion before restoring owner authority. |
| MFA policy | [Hosted MFA](https://workos.com/docs/authkit/mfa) required mode excludes SSO users. Disable alternative sign-in paths and enforce backend proof. Dashboard-team-member factor reset is separate from application-user recovery. |
| Costs | [Official pricing](https://workos.com/pricing) advertises User Management free for the first one million monthly active users and a $99/month custom-domain add-on. Neither a new paid add-on nor production account eligibility is approved or verified here. Standalone MFA entitlement, production terms and account billing must be explicitly checked before activation; do not infer coverage from User Management pricing. |

Recovery must require the current owner password, a previously enrolled and verified independently stored recovery authenticator, and an authenticated operator-issued one-use maintenance ticket. Ticket possession, mailbox access or a password-only session is insufficient. Enrollment of recovery material itself requires fresh primary password/TOTP proof. Recovery must not issue an ordinary owner session until replacement primary TOTP is verified and old sessions are invalidated atomically.

If both authenticators are lost or no recovery authenticator was enrolled, this ceremony cannot recover the owner. Do not introduce an email-only reset, hidden account or automatic pin clearing. Such a case needs separately designed and reviewed strong operator identity verification; document it as unsupported rather than silently weaken authentication.

Synthetic maintained-SDK fixtures validate application state transitions and failure handling. They cannot establish production-provider entitlement, factor limits, rate/CPU capacity, provider outage behavior or a real user's recovery experience. Keep readiness disabled until those live checks are authorized and completed.

## Optional staging contract probe — not run

`licensing-worker/scripts/provider-contract-smoke.mjs` is an explicitly opt-in **provider-write** probe, not a deployment or automatic test. It requires a private JSON configuration with `confirmedStaging:true`, `authorizedSyntheticProviderWrites:true`, identical `expectedClientId`/`stagingClientId`, an absolute `apiKeyFile` outside the repository and an operator-controlled `syntheticEmailDomain` beginning `qa.`. No secret is accepted on the command line. Run only after separate authorization with `config-file --authorized-staging-write`. Choose an isolated WorkOS staging environment with required MFA; do not use the sole owner's identity or production credentials.

The API key's generic `sk_` prefix does not certify staging. Configuration is an operator attestation, **not programmatic proof of environment**, and must be checked in the provider dashboard before execution. Also provide an absolute `outputParent` outside the repository and synchronization folders: the protected recovery manifest stores only synthetic IDs, email/external ID and cleanup state, never passwords, seeds, keys or tokens. The script has not been run against any provider. It creates UUID synthetic users, verifies exact external-ID lookup/business-error duplicate rejection, initial MFA enrollment and later challenge, independent standalone challenge, real SDK password/TOTP sealing, rejection of the old password after update, acceptance of the new password, full-session revocation and primary-factor deletion/replacement. Successful repeat TOTP use waits for a different 30-second counter. It then attempts deletion of every known factor/user and exact external-ID reconciliation after an uncertain initial create. Timeout may leave an unknown factor creation: inspect the isolated staging environment privately after any failure. No automatic retry or pricing eligibility inference is made.

Before using standalone recovery, obtain explicit account confirmation: “Does our Free User Management entitlement include calls to `/auth/factors/enroll`, `/auth/factors/:id/challenge` and `/auth/challenges/:id/verify` for a standalone TOTP factor without `user_id`, without a paid MFA product or usage charge? Are these supported for production recovery, and what are their limits?” No support message has been sent. Published pricing alone did not resolve this question.

The local maintenance implementation uses a durable nonce-bound lease and checks it around provider calls, with a 30-second remaining-lease margin beyond the configured 10-second client timeout. This prevents subsequent stale operations from proceeding in tested interleavings. A client timeout/abort does **not** prove that a remote provider mutation stopped; there is no distributed transaction between D1 and WorkOS. Uncertain responses require exact-identity/operation reconciliation and may leave orphan provider factors. Do not claim cross-service atomicity or physical exclusion of indefinitely delayed remote effects.
